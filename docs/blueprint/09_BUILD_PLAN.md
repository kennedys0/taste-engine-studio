# AI Agent Build Plan and Milestone Gates

This plan prevents a broad showcase brief from degenerating into decorative, nonfunctional pages. The agent should implement one **working end-to-end vertical slice** first and then generalize. Each milestone must have concrete evidence.

## Phase 0 — Inspect before changing anything

Read the repository, installed Taste Engine `SKILL.md`, style registry, 10 style files and conditional engineering guidance. Determine if the Vite project already exists; preserve user code/assets/working behavior. Confirm the actual package version and installation method. Record where the source files live. Do not ask the style question again: Neo-brutalism is explicitly chosen for the site.

**Gate:** Agent can name the exact 10 pack IDs, demonstrate understanding of the updated Glassmorphism material/gradient exception, and show confirmed source paths. No fabricated facts.

## Phase 1 — Product shell and content truth

Build Vite + React JSX scaffolding if needed, React Router, site layout, header, footer, Neo-brutalism homepage first viewport, `/styles`, `/installation` and a correct 404. Add route metadata approach and responsive navigation. Create content from verified Taste Engine facts.

**Gate:** Home CTA/links and install copy work; 320/390/768/1440 widths are usable; no invented marketing figures; initial `npm run build` passes.

## Phase 2 — One complete functional specimen system

Build reusable semantics and working components: image/content card, CTA, tabs, FAQ, form validation, switch, dialog/toast, search/filter/sort, empty/error/loading preview, theme preference. Label all data local/demo. Build one complete `/neo-brutalism/playground`, login simulator and sample dashboard as the first vertical slice.

**Gate:** At least one style demonstrates all P0 flows with keyboard, mobile and honest feedback. Avoid adding more style routes before this slice actually works.

## Phase 3 — Aesthetic fidelity on real routes

Implement ten style systems based on each **actual pack**, creating anatomy overrides only where necessary. Start with contrasting materials (Glassmorphism, Claymorphism, Neo-brutalism, Retro Terminal, Enterprise), then the others. Preview each at light/dark, desktop/mobile. Add full-height style hero and links to dedicated demos.

**Gate:** 10 style overview routes are visually recognizable without headings. Glass first viewport shows backdrop-filtered translucent pane over ambient light with gradient exception properly honored. None of the ten is just a palette swap.

## Phase 4 — All per-style demo routes

Use the shared functional specimen library and local fixture to implement `/:style/playground`, `/:style/login`, `/:style/dashboard` for all ten. Ensure style-specific layout variants where required. Include category navigation, interactive state selectors, proper sample labels, consistent copy and keyboard handling.

**Gate:** 40 style-related routes work, including deep refresh and 404 handling. All styles have valid light/dark variants and accessible focus.

## Phase 5 — Compare, polish and docs

Build `/compare` with two selected styles rendering the **same** specimen. Add `/about`, `/how-it-works`, `/features`, `/showcase`, `/docs`, `/anti-slop`, `/seo`, `/motion`, `/engineering`, `/faq`; do not duplicate every section indiscriminately. Add meaningful internal links, English copy, install guide/troubleshooting, external GitHub links and use cases.

**Gate:** All 54 canonical public routes present (14 core + 40 style-related) or a clearly documented intentional reduction. Comparison survives refresh and smaller screens. Info pages teach distinct facts, not recycled filler.

## Phase 6 — Release readiness

Run build, component tests, route smoke tests, browser checks at responsive widths, interaction smoke tests, keyboard/focus/contrast, CSS fallback and reduced-motion behavior, direct-link refresh, image attribution and public HTML/SEO checks. Use actual screenshots to judge style material fidelity. Fix critical problems before visual embellishment.

**Gate:** All P0 quality checks in `08_QA_ACCEPTANCE.md` verified or explicitly flagged as not completed. Public deployment strategy documented. No claim of production-readiness without build and browser proof.

## Anti-regression rules for the agent

- Do not break existing routes, handlers, demo data or theme persistence during visual refinement.
- Do not let global Neo-brutalism site tokens bleed into a different style's specimen body.
- Do not change a functional modal into a static card just to match a screenshot.
- Do not replace Glassmorphism's material-supporting gradients with flat navy because of blanket anti-slop interpretations.
- Do not pretend a simulated login talks to a real service; never store passwords.
- Do not render 30 fake disabled controls to claim component coverage. Build real working specimens.
- Do not add animation dependencies just to make the site feel “premium”.
- Do not duplicate content/data sources in ten style-specific components unnecessarily.
- Do not mark acceptance criteria done without performing the relevant check.

## Suggested agent coordination, if multi-agent capabilities exist

- **Lead/design:** Verifies Taste Engine style files, composes visual systems, reviews aesthetic material fidelity.
- **Frontend:** Owns routing, React implementation, state, responsive components and compositional variants.
- **Content/docs:** Verifies all repository claims and command snippets; drafts English page content.
- **QA/accessibility:** Performs real interaction tests, screenshot/viewport checks and keyboard audits.

If a multi-agent environment does not exist, execute these responsibilities sequentially. No imaginary sub-agent reports.
